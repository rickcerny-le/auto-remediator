## MODIFIED Requirements

### Requirement: Push bumped manifests to a per-repo branch
The system SHALL push the edited manifests — together with any `packages.lock.json` regenerated by local verification, and any source edits produced by the remediation loop — as a commit to a deterministic per-repository branch named `autoremediator/dependency-updates`, based on the repository's target branch. If the branch does not exist it SHALL be created from the target branch head; if it exists it SHALL be updated. The push SHALL occur only after verification has been attempted, and SHALL NOT occur at all when the change was rejected and not repaired. Artifacts generated purely for verification, such as a generated `NuGet.config`, SHALL NOT be pushed.

When the remediation loop contributed source edits, the push SHALL additionally require a reviewer's approval, and SHALL push the approved proposal's recorded change set rather than recomputing it.

The push SHALL remain a compare-and-swap against the branch head the change was based on, so a push whose branch has moved SHALL be rejected rather than overwrite it. This matters more once approval may arrive long after the change was computed.

#### Scenario: Branch is created on first run
- **WHEN** an update run pushes changes for a repository that has no `autoremediator/dependency-updates` branch
- **THEN** the branch is created from the target branch head with a commit containing the edited manifests

#### Scenario: Branch is reused on subsequent runs
- **WHEN** an update run pushes changes for a repository that already has the branch
- **THEN** the same branch is updated rather than a new branch being created

#### Scenario: Regenerated lock file is included in the commit
- **WHEN** verification regenerated a `packages.lock.json` for a repository that commits one
- **THEN** the pushed commit contains the regenerated lock file alongside the edited manifests

#### Scenario: Agent source edits are included in the commit
- **WHEN** an approved proposal repaired a compile break
- **THEN** the pushed commit contains the agent's source edits alongside the manifest and lock-file changes

#### Scenario: An agent-repaired change is not pushed before approval
- **WHEN** the remediation loop repaired a change and no reviewer has approved it
- **THEN** no commit is pushed to the per-repo branch

#### Scenario: A stale approval does not overwrite the branch
- **WHEN** an approved proposal is pushed after its update branch has moved
- **THEN** the push is rejected and the branch is left as it was

#### Scenario: Verification artifacts are excluded from the commit
- **WHEN** a push occurs after verification generated a `NuGet.config` in the working tree
- **THEN** that generated file is not part of the pushed commit

#### Scenario: A rejected change is never pushed
- **WHEN** verification rejected the computed change and the remediation loop did not repair it
- **THEN** no commit is pushed to the per-repo branch

### Requirement: Open or refresh a single pull request
The system SHALL ensure exactly one active pull request from the per-repo branch into the target branch: it SHALL create the pull request if none is active, and reuse the existing one otherwise (the refreshed branch updates it). The pull request SHALL include a summary of the applied updates (package, from → to) and SHALL report the local verification outcome — stating that the change was verified locally, or stating explicitly that verification was skipped and why, so a reviewer is never left to assume a change was verified when it was not. The description SHALL also name the repository's own CI as the authority that additionally runs the tests.

When the remediation loop contributed source edits, the description SHALL disclose that the pull request contains **AI-authored source edits**, state how many attempts were made, and link the transcript. A reviewer SHALL NOT have to infer AI involvement from the diff.

Where the change was held for review, the description SHALL state when it was verified and against which commit, so a reviewer is not left to assume a verification is fresher than it is.

#### Scenario: Pull request is created when none exists
- **WHEN** the branch has been pushed and no active PR from it exists
- **THEN** a pull request is created into the target branch with a title and a description listing the updated packages and their version changes

#### Scenario: Existing pull request is reused
- **WHEN** an active pull request from the branch already exists
- **THEN** no duplicate is created; the existing pull request is reused (its head now reflects the new commit)

#### Scenario: Verified change is reported as verified
- **WHEN** local restore and build succeeded for the change
- **THEN** the pull request description states that the change was verified locally by restore and build

#### Scenario: Skipped verification is reported explicitly
- **WHEN** verification could not run or its result cannot be trusted
- **THEN** the pull request description states that verification was skipped and gives the reason

#### Scenario: AI-authored edits are disclosed
- **WHEN** an approved proposal repaired the change with source edits
- **THEN** the pull request description states that it contains AI-authored source edits, gives the attempt count, and links the transcript

#### Scenario: The age of the verification is disclosed
- **WHEN** an approved proposal is opened as a pull request
- **THEN** the description states when the change was verified and the commit it was verified against

#### Scenario: A purely mechanical bump is not labelled as AI-authored
- **WHEN** a run verifies without the remediation loop being invoked
- **THEN** the pull request description makes no claim of AI-authored edits
