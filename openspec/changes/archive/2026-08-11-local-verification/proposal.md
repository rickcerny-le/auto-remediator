## Why

Today a run bumps manifest text and opens a pull request without ever compiling the result: `update-execution` explicitly delegates all validation to the target repository's CI. That leaves two gaps. First, the bump set is unverified — restore-time conflicts outside the `Orion180.*` family (version conflicts, downgrades) and compile/API breaks reach the PR unseen. Second, and concretely broken: a repository that commits `packages.lock.json` gets a PR whose lock file still lists the old versions, which fails restore in locked mode (`NU1004`) by construction. A lock file cannot be regenerated from feed metadata — only a real `dotnet restore` produces one.

This slice adds a **local** verification step before the push, which is also the signal the AI remediation loop (Slice 5) needs. Building in-job rather than polling the PR's CI keeps the run a single synchronous process — CI-feedback would require suspending and resuming runs across minutes, publishing knowingly-broken PRs, and spending the target team's build minutes per iteration.

## What Changes

- **New**: materialize the repository's working tree in the job by downloading it from Azure DevOps as a zip archive at a known commit — no `git` binary and no clone, reusing the existing PAT-authenticated client.
- **New**: apply the computed manifest edits into that tree, then verify with `dotnet restore`, and only if restore succeeds, `dotnet build`. Restore gates build.
- **New**: capture verification diagnostics (structured errors with file/line where available, plus the full log) and persist the logs as run artifacts in blob storage.
- **New**: include any `packages.lock.json` regenerated by restore in the pushed commit, fixing locked-mode repositories.
- **MODIFIED**: the run pipeline splits the current `Applying` stage — which today both edits manifests and pushes — into apply-to-tree, `Verifying`, and `Pushing`. Nothing is pushed before verification runs.
- **MODIFIED**: a *dependency-related* verification failure (restore conflict, compile error) ends the run in a new terminal status without opening a pull request, recording the diagnostics.
- **MODIFIED**: an *environment* failure (SDK unavailable, `global.json` unsatisfiable, feed unreachable, tree download failure) degrades gracefully — the run pushes and opens the pull request anyway with a note that verification was skipped, preserving today's behavior as the floor.
- **MODIFIED**: the remediation worker's container image final stage moves from the .NET runtime base to the .NET SDK base so the job can restore and build. All target repositories are .NET 8/10, so a single `sdk:10.0` image suffices.
- **MODIFIED**: the run detail API and page surface the verification outcome and a link to its logs.
- Tests remain out of scope — the target repository's own Azure DevOps CI stays the authority on the pull request and continues to run the full build, tests, and analyzers.
- The AI remediation loop (Slice 5) is out of scope; this slice only produces the diagnostics it will consume.

## Capabilities

### New Capabilities
- `local-verification`: materializing the repository tree in the job, running gated `dotnet restore` → `dotnet build` against the edited manifests, classifying the outcome as verified / dependency-failure / environment-skip, and capturing diagnostics and logs as run artifacts.

### Modified Capabilities
- `update-execution`: the "Validation delegated to the repository CI" requirement is replaced — local restore/build now verifies the bump set before any push, while the repository's CI remains the authority on the pull request. The edit set additionally carries a regenerated `packages.lock.json` when the repository uses one.
- `run-orchestration`: the run state machine gains `Verifying` and `Pushing` stages between `Applying` and `CreatingPR`, plus a terminal status for a verification failure that produced no pull request.
- `azure-devops-connectivity`: adds retrieval of the repository's full tree as a zip archive at a specified commit, alongside the existing manifest discovery.
- `pull-request-authoring`: the push includes a regenerated lock file when present, and the pull-request description reports the verification outcome, including an explicit note when verification was skipped.
- `container-images`: the `remediation` worker's final stage is built on the .NET 10 SDK base rather than the runtime base, as it shells out to `dotnet restore`/`dotnet build`.
- `run-observability-ui`: the run detail API and page expose the verification outcome and a link to the captured verification logs.

## Impact

**Code**
- `AutoRemediator.Infrastructure/Remediation/RemediationRunner.cs` — stage restructure; verification inserted before the push.
- `AutoRemediator.Domain/RemediationRun.cs` — `RunStatus` gains `Verifying`/`Pushing` and the verification-failure terminal status; the run carries a verification outcome.
- `AutoRemediator.Infrastructure/Configuration/RemediationRunStore.cs` — persist the new status and verification outcome.
- `AutoRemediator.Infrastructure/AzureDevOps/` — tree-as-zip download on `IAzureDevOpsClient`; commit path extended for the lock file.
- `AutoRemediator.Infrastructure/Verification/` (new) — tree materialization, `NuGet.config` generation, restore/build process execution, diagnostic parsing.
- `AutoRemediator.Api/Features/Runs/`, `AutoRemediator.Contracts/Dtos/RunDtos.cs`, `AutoRemediator.Web` run detail — surface the verification outcome and log link.
- `src/AutoRemediator.Worker.Remediation/Dockerfile` — SDK final stage.

**Dependencies and systems**
- Restore authenticates to the private feed via a generated `NuGet.config` using the PAT already resolved for feed version lookups; no new secret is introduced.
- The remediation job now needs writable temp disk and outbound package restore, and its image grows substantially (runtime → SDK base). Locally the worker runs as an Aspire project on the host, where the SDK is already present, so local development needs no new setup.
- Run duration increases by the cost of a restore and build per run.

**Not affected**
- Analysis, policy, and family alignment are unchanged — verification consumes their output rather than replacing it.
- The scheduler, queueing, and per-repo branch/PR idempotency are unchanged.
