## MODIFIED Requirements

### Requirement: Produce edited manifest contents
The system SHALL apply the computed updates by editing the relevant manifest contents (`Directory.Packages.props` `PackageVersion`, `*.csproj` `PackageReference`), setting each updated package's version to its target while leaving all other content unchanged. Editing SHALL operate on the manifest text and SHALL NOT require a local clone. Where the repository commits a `packages.lock.json`, the change set SHALL additionally carry the lock file as regenerated by local restore, since a correct lock file cannot be derived from feed metadata alone.

#### Scenario: A package version is updated in place
- **WHEN** an update sets `Orion180.Core` to `2.0.0` in a `Directory.Packages.props` that pinned `1.0.0`
- **THEN** the returned manifest content has `Orion180.Core` at `2.0.0` and every other package and surrounding content unchanged

#### Scenario: Only manifests with a target package are changed
- **WHEN** the update set is applied across a repository's manifests
- **THEN** only manifests that declared an updated package are returned as changed, and manifests without any updated package are not modified

#### Scenario: A committed lock file is carried in the change set
- **WHEN** the repository commits a `packages.lock.json` and local restore rewrites it for the bumped versions
- **THEN** the change set contains the regenerated lock file alongside the edited manifests

## ADDED Requirements

### Requirement: Local verification precedes the pull request, CI remains the authority
The system SHALL verify the computed change locally before pushing, by restoring and building the repository in-job against the edited manifests. Local verification is a fast, approximate signal — it deliberately does not run the repository's tests, analyzers, or custom build targets — and the repository's own Azure DevOps CI running against the opened pull request remains the authority on correctness. A locally-verified change SHALL NOT be treated as guaranteed to pass that CI.

#### Scenario: A change is verified before any push
- **WHEN** an update run computes a non-empty update set
- **THEN** it restores and builds the edited tree locally before pushing a commit or opening a pull request

#### Scenario: Tests remain the repository CI's responsibility
- **WHEN** local verification succeeds
- **THEN** no tests were run locally and the pull request is still validated by the repository's own Azure DevOps CI

#### Scenario: A locally-rejected change opens no pull request
- **WHEN** local verification positively rejects the change with dependency or compilation diagnostics
- **THEN** no commit is pushed and no pull request is opened for that run

## REMOVED Requirements

### Requirement: Validation delegated to the repository CI
**Reason**: The blanket prohibition on local building blocked both the lock-file regeneration this slice needs and the compiler diagnostics the AI remediation loop will consume. Local restore/build is now performed as a pre-push signal.

**Migration**: Replaced by "Local verification precedes the pull request, CI remains the authority", which preserves the important half of the original guarantee — the repository's own Azure DevOps CI is still the authority on the pull request, and tests are still never run locally.
